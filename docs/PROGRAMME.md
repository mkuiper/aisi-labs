# Programme charter

Australian AI Safety Institute · AISI AI Labs

## Purpose

Provide Australian Public Service staff with hands-on exposure to contemporary AI tools for professional development and personal upskilling. Staff should be able to experiment, make small projects, understand the underlying concepts and judge the results. The environment is for learning, not the processing of official business information.

## Audience and approach

The audience includes people new to terminals and coding, as well as experienced technical staff. Direct tool launch and open projects support experienced learners. Short illustrated explanations, public practice datasets, guided projects and a simulated terminal support beginners. Learners can move between these approaches without completing a mandatory course sequence.

The persistent Omarchy help link gives first-time users an offline desktop
orientation and shortcut cheat sheet, with a link to the terminal simulation.
Facilitators must verify the bindings on their particular learning image.
Fullscreen and close-window controls are presented first, with save-work
cautions. Learn questions use practical scenarios and choice-specific
explanations; they are optional and do not record answers or scores.

First 20 minutes offers an optional route through the existing first project,
including offline preparation. Finish session separates manual handover steps
from the explicit local key-forgetting action; it cannot certify logout or
device readiness. The improvement schedule sets proposed pilot and deployment
gates, not approved dates or automatically scheduled work.

## Creative media and keeping current

Web & media includes image/video learning profiles and a no-install workflow
introduction. Learners can start with a fictional storyboard without generating
anything. Optional hosted exercises require appropriate learning accounts and
cost checks; review likeness, rights, public-sharing settings and output labels.
Keep current links to benchmark methods and research discovery. Rankings are
task-specific evidence, not government approval or a procurement shortlist.
These additions neither install creative software nor automatically update tools.

## Non-negotiable boundaries

- Input ONLY public information. Never enter OFFICIAL or higher-classified material, internal work files, or non-public personal information.
- The supplied fictional examples are public practice material. Removing names, paraphrasing or inventing replacements within an internal document does not make that document public.
- NEVER connect the learning laptop to government networks or systems, including government Wi-Fi, Ethernet, VPN, remote desktop or another bridging connection.
- Use a designated separate non-government learning network. Do not connect government accounts, email, storage, internal APIs or MCP servers accessing government systems.
- Use dedicated learning credentials with access limited to the learning services. API keys belong only in authentication settings, never in model prompts or project content.
- Use tools responsibly: respect privacy and rights, inspect permissions and changes, check evidence, control costs and avoid impersonation or harmful activity.

These are programme rules set for this learning environment. They do not purport to summarise every department's policy or determine whether a product is approved for official work.

A separate network and public-only inputs do not exempt a government-owned
learning laptop from applicable product or device restrictions. The deployment
owner must check those requirements before enabling services. The Web chat
directory includes a reference-only DeepSeek profile explaining PSPF Direction
001-2025; it provides no chat launch or model installation. Educational inclusion
is not permission to use a restricted product through another host.

## Deployment model

A department installs a reviewed learning image on suitable repurposed laptops. Devices use a separate non-government learning network with internet access for cloud tools. The hub, learning material and authored simulations run locally. Some tools use cloud models; local model inference is optional and must be tested against the hardware available.

The current deliverable is the application and deployment documentation. A bootable or managed laptop image has not yet been built or approved. Device and network isolation must be implemented and verified by the deployment owner; the app cannot provide that guarantee.

## Ownership

- Programme owner: approves learning outcomes, tool inclusion and the public-information boundary.
- Image and network owner: prepares the device, enforces separation, handles patching and recovery, and records release acceptance.
- Facilitator: introduces the boundaries, helps staff authenticate to learning services and handles support escalation.
- Learner: uses only public inputs, reviews actions and results, manages permitted credentials and reports mistakes promptly.

Each departmental deployment should nominate these roles and publish its support and incident contacts before handing out devices. No staff names, email addresses or scores are required by the hub.

## Measuring success

Observe whether learners can open a tool, distinguish a model from its harness, explain a tool call, inspect a generated result, recognise information they must not input, and finish a small public practice project. Use voluntary feedback and observed usability sessions. Bookmarking a lesson or ticking a checklist is self-reporting, not certification of competence.

## Release status

This is a working learning preview. The rules are visible throughout the app and acknowledged before project creation, tool launch or key setup. Acknowledgement applies to the current hub server session and shared Linux account; it is not user authentication, evidence of network isolation or a substitute for deployment controls.
